CYBERSECURITY, WITHOUT THE HEADACHE

PHP2Shell, AI, FBI warnings, and the websites that went offline

By Prakarshi Polina Published October 28, 2026 8 min read

Imagine opening the internet one morning and discovering that government websites, online services, and familiar platforms are temporarily going offline — not necessarily because they were hacked, but because staying online could be the bigger risk.

That was the kind of situation that unfolded around PHP2Shell in October 2026. Two critical vulnerabilities in PHP triggered urgent security warnings, emergency updates, and precautionary shutdowns. There was another detail that made the story especially interesting: AI tools had helped security researchers investigate the weaknesses.

So let's break it down without turning this into a lecture full of complicated cybersecurity vocabulary.

First things first: what even is PHP?

Imagine a website as a restaurant. The page you see is the dining area, but behind the scenes there's a kitchen doing the work: retrieving information, processing forms, and talking to databases.

PHP is one of the technologies that can power that behind-the-scenes work. It runs on web servers and helps websites generate dynamic pages. You might never notice it when you visit a website, but it can be part of what makes the website function.

Here's why that matters: if a problem exists in one individual website, the owner may only need to fix that website. But if a weakness exists in the underlying programming language, many different websites and services could need to check their systems.

That's the bigger picture behind PHP2Shell. The concern wasn't simply one badly written website. It was a weakness in PHP itself, which is used by a huge range of web applications and services.

Okay, so what was PHP2Shell?

PHP2Shell is the name associated with two critical PHP vulnerabilities disclosed on October 21, 2026:

  • CVE-2026-109618: an out-of-memory handling flaw that can lead to memory corruption.
  • CVE-2026-109619: a use-after-free flaw involving internal state that may point to memory that has already been freed.

Both vulnerabilities received a CVSS v4.0 severity score of 9.2 out of 10 — Critical. Under certain conditions, an attacker could exploit them to run code on an affected server without first logging in.

Cybersecurity professionals call this unauthenticated remote code execution. In everyday language, it means someone could potentially make a vulnerable computer run instructions from a distance without passing through the normal login process.

VULNERABILITY 01

Out-of-memory handling

9.2/10 CRITICAL · CVSS v4.0

CVE-2026-109618

What's the problem?

When PHP runs out of memory, it can interrupt the current operation. In certain situations, some internal request data may not be fully prepared, but cleanup code may still treat that data as if it were ready to use.

Why should we care?

Mishandling that memory can cause memory corruption. Under the right conditions, an attacker could potentially use it to execute code on the affected server.

VULNERABILITY 02

Use-after-free

9.2/10 CRITICAL · CVSS v4.0

CVE-2026-109619

What's the problem?

A program can release memory when it no longer needs it. The danger appears when some internal state still points to that memory after it has been freed.

Why should we care?

A later request may use that stale information before it has been correctly reset. Under certain conditions, this can contribute to memory errors and remote code execution.

A QUICK REALITY CHECK

A score of 9.2 means the vulnerabilities are rated Critical. It does not mean that 92% of websites were hacked, or that every website running PHP was successfully compromised. Risk, exposure, and confirmed compromise are three different things.

Wait — AI helped find these vulnerabilities?

Yes, and this is one of the most interesting parts of the story. AI tools were used as part of security research into the PHP flaws. But the details matter: it wasn't the FBI simply asking an AI chatbot to scan the internet and then discovering everything.

Security researchers at organisations including Calif, Wiz, and OpenAI were involved in discovering and investigating the issues. Reporting from Wiz describes how AI models and research tools helped investigate the vulnerable code, develop and test exploits, and validate fixes.

Think of AI as a very fast research assistant. It can help a specialist examine complicated code, explore possible explanations, test ideas, and investigate why something behaves unexpectedly. The researchers still need to verify what the tools produce and work with software maintainers to get a fix developed and tested.

The vulnerabilities were particularly tricky because they involved how PHP handles memory and internal state. Those aren't always easy problems to identify just by looking at a website from the outside.

SO, WHAT DID THE FBI DO?

The FBI's cyber division published a critical PHP vulnerability alert. The discovery work and the government warning are related parts of the same story, but they are not the same event: researchers investigated the flaws, while agencies warned organisations about the risk and the need to act.

There is a bigger lesson here, too. AI can help defenders find weaknesses sooner, but the same general capabilities can also help attackers analyse vulnerabilities and adapt their techniques. AI isn't automatically good or bad; how people use it matters.

Why were the FBI and other security agencies warning people?

When a flaw can potentially let an attacker run code on a server without logging in, organisations need to take it seriously. A compromised server could put applications, data, and other systems within reach at risk, depending on the server's permissions and setup.

The FBI published a critical PHP vulnerability alert, and other cybersecurity agencies also advised organisations to identify affected systems, apply fixes, and consider temporary shutdowns if they could not protect a vulnerable service in time.

Why take a website offline? Think of it like closing a shop for a short time because the lock on its front door may be defective. Closing is inconvenient, but it can be safer than leaving the door open while the problem is being fixed.

For an organisation that provides public services, taking a site offline can be disruptive. But it may be a deliberate safety decision rather than evidence that an attacker has already broken in.

Which organisations took websites or services offline?

This is where the story went from a technical security advisory to something people could actually notice. Reuters reported that a number of governments, public institutions, and businesses temporarily took websites or online services offline or restricted access while they dealt with the PHP vulnerabilities.

These are examples reported in connection with the precautionary response. They should not be read as a list of organisations confirmed to have been hacked.

Here's the distinction I think is really important: a service being unavailable does not automatically mean its data was stolen. In several cases, organisations said the action was precautionary. The shutdown itself was part of the response to the risk, not proof that the vulnerability had been exploited against that organisation.

Does that mean these companies were hacked?

Not necessarily. There are three different situations that are easy to mix up:

  • Vulnerable: a system contains a weakness that could be exploited.
  • Under attack: someone is trying to exploit a weakness.
  • Compromised: an attacker has successfully gained unauthorised access or control.

Those are not interchangeable. A company can discover that a system is vulnerable and take it offline before an attacker successfully exploits it. In fact, that is exactly the kind of preventive action security teams want organisations to take.

The responsible way to describe this incident is that multiple organisations restricted or temporarily took services offline in response to the PHP2Shell risk. Do not label every organisation in this list as "hacked" unless a reliable source confirms that specific claim.

Why did one software problem affect so many different places?

Websites can look completely different on the surface while relying on the same underlying software. One may be a public information portal, another may be a digital library, and another may be a company's online service. If their server environments use affected PHP versions, they may all need to assess the same underlying vulnerability.

Imagine finding a problem with a particular type of lock used in thousands of buildings. The buildings are not all owned by the same company, and they don't all contain the same things. But everyone using that lock may need to check whether theirs is affected and arrange a repair.

That is why the response involved software maintainers, hosting providers, cloud services, security researchers, and organisations running their own websites.

What should organisations do?

If a company runs PHP, its security team should check the official PHP guidance and determine which systems are affected. The exact response depends on the PHP version, the deployment, and the vendor's instructions.

  • Identify PHP installations across websites, servers, and products managed by vendors.
  • Prioritise systems exposed to the internet.
  • Install the appropriate security updates and verify that the fixed version is running.
  • Review logs and investigate signs of compromise where appropriate; patching alone does not prove that no earlier intrusion happened.
  • If a vulnerable system cannot be safely patched in time, follow official guidance and assess whether it should temporarily be taken offline.

PHP announced fixes for supported branches including 8.5.12, 8.4.27, 8.3.36, and 8.2.35 for these vulnerabilities. Check the official PHP advisory for the latest guidance and the version appropriate to your installation. Older unsupported releases may require a supported-version upgrade rather than a simple patch.

My takeaway

The part I find fascinating is how many different things came together in one story: a programming language, hard-to-find memory bugs, AI-assisted security research, government warnings, and organisations making the difficult decision to temporarily switch off services.

AI helped researchers investigate the flaws, but it did not remove the need for human expertise, testing, responsible disclosure, or software maintainers to release fixes.

And when websites went offline, that didn't automatically mean hackers had won. In many cases, taking a service offline was a defensive decision intended to reduce risk while updates were applied.

We tend to think of the internet as millions of separate websites. Underneath, many of them depend on shared building blocks. That makes those building blocks incredibly useful — and keeping them secure everyone's business.

So the next time a cybersecurity headline sounds like a story about a faraway server, remember: the consequences can reach much further than the code where the problem began.

And that's probably a good reason to pay attention.
